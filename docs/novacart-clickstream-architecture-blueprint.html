Versioning & Compatibility Rules

  • Schema Registry compatibility mode: BACKWARD (new consumers can read old messages)
  • Adding optional fields with defaults: allowed without version bump
  • Adding required fields or removing any field: major version increment, migration plan required
  • Schema subject naming: clickstream-event-value
  • All schemas pinned by schema ID in Kafka message headers

2 Front-End Event Collection SDK

Technology

JavaScript (browser)Swift (iOS)Kotlin (Android)

Web SDK Behaviour

  • Auto-generates anonymous_id on first load; persists in localStorage
  • Buffers events in memory queue (max 50 events or 5 seconds, whichever first)
  • Flushes via Beacon API (navigator.sendBeacon) on page unload; falls back to fetch
  • Compresses payloads with CompressionStream (gzip) where supported
  • Retry on failure: exponential backoff — 1s, 2s, 4s, 8s — max 4 retries; failed events persist in sessionStorage
  • Never sends directly to Kafka; always POST to ingestion API

Transport Endpoint

POST /events/batch
Content-Type: application/json
Authorization: Bearer <sdk_token>

{
  "sdk_version": "1.0.0",
  "sent_at": "2025-11-09T14:32:00Z",
  "events": [ { ...event }, ... ]
}

Mobile SDK

  • Same event model and batching strategy as web SDK
  • Background upload using URLSession.background (iOS) / WorkManager (Android)
  • Persists queue to SQLite on device; survives app kill
  • Max batch: 100 events or 10 seconds

3 Edge Ingestion API

Technology

FastAPINGINX (ingress)Kubernetes (deployment)

API Responsibilities (in order)

  1. Auth validation — Bearer token checked against token store (Redis); reject 401 immediately
  2. Rate limiting — 10 000 events/s per IP via NGINX limit_req; 429 with Retry-After header
  3. Payload validation — Pydantic v2 against event contract; batch rejected 422 if any event malformed (configurable: fail-fast or quarantine-bad)
  4. Correlation ID — X-Correlation-Id generated (UUID v4) and attached to every event and response
  5. Geo-IP enrichment — MaxMind GeoLite2 database lookup; appends country, region, city
  6. User-Agent parsing — ua-parser2; appends device_type, os, browser
  7. Ingestion timestamp — server-side UTC appended as ingestion_timestamp
  8. Schema Registry check — schema ID resolved before Kafka publish
  9. Async Kafka publish — non-blocking; partition key = session_id; topic = clickstream.raw
  10. Invalid routing — failed validation events published to clickstream.invalid

6 Sessionization Engine

Session Rules

  • New session triggered after 30 minutes of inactivity
  • New session triggered on authentication state change (anonymous → authenticated)
  • Anonymous-to-authenticated stitching: when user_id appears, back-fill session with user identity
  • Session state persisted in Spark checkpoint storage (RocksDB state backend)

Advanced Processing

  • Markov chain transitions — first-order transition probability matrix between event types; updated every 15 minutes; stored in Delta Lake and Redis
  • Journey embeddings — event-type sequences encoded via sliding window; fed to recommendation model
  • Sequence scoring — likelihood score for a session reaching conversion; used for real-time intervention triggers
  • Funnel progression — page_view → product_view → add_to_cart → checkout_started → purchase_completed step counts and drop rates

12 Reliability & Failure Handling

Dead-Letter Queue Strategy

  • Schema failures → clickstream.invalid (inspect and fix schema, replay)
  • Processing failures after 3 retries → clickstream.deadletter (isolated, alerting)
  • Poison messages tagged with failure_reason and original_offset headers
  • DLQ inspector service monitors both topics; auto-alerts on sustained volume

Replay Tooling

  • Spark jobs use checkpointed offsets — restart from last committed offset automatically
  • Manual replay: replay-tool --topic clickstream.raw --from-offset 12345 --to-offset 99999
  • Bronze Delta Lake is immutable — any Silver/Gold job can be re-run from Bronze without data loss

Chaos Scenarios & Mitigations

ScenarioMitigation
Kafka broker failureReplication factor 3; min ISR 2; producers retry with backoff
Spark job crashCheckpointed state; k8s restarts pod; resumes from last committed offset
Out-of-order burst30-min watermark absorbs late events; extreme lates to dead-letter
Partition reassignmentSession_id partitioning ensures no cross-partition journey splits
ClickHouse unavailableKafka sink connector buffers; replays when ClickHouse recovers

PII & GDPR

  • user_id stored as SHA-256 hash in all analytics columns; mapping table encrypted at rest (AES-256)
  • search_query keyword-extracted only; raw query never persisted past Bronze
  • GDPR deletion workflow: event deletion request triggers Bronze → Silver → Gold → ClickHouse scan; user hash zeroed; audit log written
  • Consent flag carried on every event; non-consented events routed to consent-filtered topic, not analytics
  • Schema lineage tracked in Atlas / DataHub; every column tagged with data classification (PII / non-PII)

Encryption

  • All Kafka traffic: TLS 1.3
  • Delta Lake at rest: AES-256 via object storage server-side encryption
  • ClickHouse at rest: encrypted volumes
  • Service-to-service: mTLS via Istio service mesh

16 Recommended Implementation Order

  1. Event contract — Pydantic models + Avro schemas + Schema Registry setup. Nothing else can be built without this.
  2. Edge Ingestion API — FastAPI service, runs locally with a mock Kafka producer for dev/test.
  3. JavaScript SDK — integrates with ingestion API; drives all web traffic.
  4. Kafka cluster + topics — baseline 3-broker cluster; configure all topics and ACLs.
  5. Spark Bronze job — raw events land in Delta Lake; proves end-to-end connectivity.
  6. Spark Silver job — dedup, bot filter, PII mask, URL parse.
  7. Sessionization engine — stateful windowing; produces session objects.
  8. ClickHouse + Kafka Connect sink — analytics data flowing into serving layer.
  9. Grafana dashboards — operational visibility from day one of data flowing.
  10. Click-path reconstruction + Markov chains — behavioral analytics layer.
  11. Recommendation pipeline — Redis feature store; online serving API.
  12. GDPR deletion workflow + schema lineage — governance layer, required before production traffic.
